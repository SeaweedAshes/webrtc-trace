WebRTC Wav2Lip Lab Implementation Log

This document records every folder-level modification for the dedicated WebRTC Native + Wav2Lip freeze-concealment system. The trace/replay WebRTC code is intentionally kept separate.

Current Design Decisions

Decision Selected Value Reason
Native checkout ~/webrtc-wav2lip-native Separate WebRTC tree for Wav2Lip integration only. This avoids contaminating trace/replay experiments.
Lab directory ~/webrtc-wav2lip-lab Holds scripts, configs, runtime outputs, and documentation outside the native checkout.
Wav2Lip mode Option 1, chunk-based generation Prioritizes research validation and debugability before optimizing for streaming latency.
IPC localhost TCP control + local file data path Simple, inspectable, and easy to replace with shared memory later.
Trigger policy Split generation risk and render switch Generation starts before visible stall: 20 ms monitor, 60 ms render-risk generation, and at least 80 ms missed-render gap before switching to generated frames.
Recovery policy Stable real-frame return Once generated playback is visible, native waits for 3 consecutive real frames and 120 ms of stable real arrivals before returning to the original stream. Immediate return is still available with an environment variable.

Implementation Notes

The first implementation uses file paths in TCP requests rather than raw frame bytes. This is slower, but it makes failures reproducible because every request has a saved audio file, face image, output path, and CSV log row.

When latency becomes the bottleneck, the data path can be replaced with a shared-memory ring buffer while keeping the same policy and state-machine structure.

The native receiver can write face frames as PPM because that is simple in C++. The Python Wav2Lip server converts non-JPG/PNG face inputs to PNG before invoking Wav2Lip.

The default native TCP endpoint is 127.0.0.1:19090, matching run_wav2lip_server.sh. It can be overridden with WEBRTC_WAV2LIP_HOST and WEBRTC_WAV2LIP_PORT.

GPU inference is supported through the existing Wav2Lip implementation: inference.py uses CUDA automatically when torch.cuda.is_available() is true. The TCP server now prints gpu_info at startup and supports --require-gpu so experiments do not silently fall back to CPU.

The persistent server wav2lip_persistent_server.py keeps the Wav2Lip model and face detector loaded in one GPU process. It avoids per-request Python subprocess startup and checkpoint loading, and it writes generated PPM frames directly instead of going through an MP4 decode path. Startup warm-up is enabled by default so the first concealment request does not pay the initial CUDA/model path cost.

Face detection is no longer repeated for every request when the incoming receiver frame shape is unchanged. The persistent server caches the last detected face coordinates and reports face_detect_ms plus face_cache_hit in the CSV log.

The receiver audio chunk length is configurable at runtime through WEBRTC_WAV2LIP_AUDIO_CHUNK_MS. This supports online experiments where shorter audio chunks generate shorter video chunks, reducing concealment startup delay. benchmark_persistent_chunks.py measures latency, output duration, and latency/output ratio for multiple chunk sizes against a running persistent server.

Online mode now separates audio context from playback hop. Native can push a rolling audio context to the persistent server using WEBRTC_WAV2LIP_STREAM_AUDIO_CONTEXT=1, then trigger generate_tail with WEBRTC_WAV2LIP_TAIL_MS. This avoids waiting for a fresh 500 ms audio file at freeze time; the server already has the latest context and returns only the tail frames needed for playback.

The real concealment target uses the last normal remote frame, not a fixed test image. Native now streams that last-good frame to the server during healthy video playback through set_face_context. The server caches the face crop/tensor and can warm the current face+audio path before a freeze occurs. During freeze, generate_tail can use <face_context>, avoiding face-file writes and face detection on the freeze-critical path.

Generated-frame playback is now implemented for the native GTK renderer. The Python server extracts generated frames as PPM files; native code loads those frames and plays them at 25 fps while the real remote stream is stalled. Playback is now queue-based rather than a short modulo loop, and native requests the next generate_tail chunk when the queue has at most WEBRTC_WAV2LIP_PREFETCH_THRESHOLD_FRAMES generated frames remaining. With WEBRTC_WAV2LIP_ALWAYS_ON=1, native also refreshes the generated queue during normal real-video playback; later freezes can switch to prepared frames immediately instead of paying the first inference latency at freeze onset. A receiver-side test freeze flag, WEBRTC_WAV2LIP_TEST_FREEZE_AFTER_MS, exists only for local verification; normal runs use real render gaps.
